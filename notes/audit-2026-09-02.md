## 1. Contradictions between rule documents

These matter most: a reader following one file violates another.

### 1.1 Classes: banned in FORMATTING.md, shown as canonical in formatting_blocks.md

- `FORMATTING.md:70` — "No classes, no prototypes, no mutation via shared state".
- `drafts/formatting_blocks.md:17` — a `class Logger` block with methods, presented
  as the module-level catalog entry, and `FORMATTING.md:141` links that catalog
  as authoritative.

One of the two is wrong. Either soften FORMATTING.md ("classes only for stateful
services such as a logger") or delete the class entry from the catalog.

### 1.2 `_by_` on a function name: banned in README, demonstrated in demos

- `README.md:160` and `drafts/var_names.md`: "A bare `<noun>_by_<key>` is
  always data, never a function. Lookup is bracket access, not a call."
- `demos/items_by.js:5` — header comment says
  "`<singular>_by_<prop>(prop)` → lookup function".
- `demos/items_by.js:37` — defines `function item_by_name(name)` (empty body).

The demo predates the ruling in `drafts/naming_markers.md:38` and was never
updated. The demo also uses `inventory_grouped_by_type` (line 18) for a
countable noun, which `naming_markers.md:36` retired ("`_grouped_by_` retired
from data names except invariant plurals"). Its local accumulator is named
`map` (line 27) where `drafts/return_out.md` requires `out`.

### 1.3 Standalone `_to_` functions: discouraged in naming_markers.md, demonstrated in demos

- `drafts/naming_markers.md:39` — "Standalone conversions prefer `_from_`
  ... `_to_` for method position, where the source is the receiver."
- `demos/item_to.js:4,14` — standalone `deg_to_rad`, `rad_to_deg`,
  `tuple_to_range`, `range_to_tuple`, with a header comment "always a function".

Either the ruling should carve out symmetric unit conversions, or the demo
should be rewritten as `rad_from_deg` / `range_from_tuple`.

### 1.4 Executable entry: `main();` in FORMATTING.md, `cli(main);` in cli_main.md

- `FORMATTING.md:34` — "Call `main();` immediately after `require` statements".
- `drafts/cli_main.md` — "`cli(main);` takes the place of the bare `main();`
  call in the executable skeleton", with a `Promise.try` rationale.
- `formatting.html` still shows `main();` in the file-anatomy section.

FORMATTING.md is the normative spec and does not mention `cli` at all. Add a
sentence there and update the executable skeleton, or mark cli_main.md as
"only for projects that depend on node-helpers".

## 2. Errors in published examples

### 2.1 Vue form example has typos that would silently break the form

`vue2/vue-form.md:8,12,16` use `v-modle` (four times). Vue 2 treats an unknown
attribute as a plain HTML attribute, so the binding never happens and no warning
is raised. `vue2/vue-form.md:18` has `clas=` for `class=`. The classes `mg10`,
`mi10`, `flex-row`, `form-row-center` are never defined anywhere in the repo.

### 2.2 README "References" section is an orphaned fragment

`README.md:203-219` contains an `Object.groupBy` snippet and a lone line
`const items_by_anim = items_group_by_anim(items);` under a heading
"References" with no prose. It reads as a scratch area that leaked into the
public README. Move it into a draft or delete it.

### 2.3 Unfinished phrase entry

`README.md:65` — "Error Flood – scenario with 75% errors (?)". The question
mark is the author's own doubt; either define it or drop it.

### 2.4 AI residue in the normative spec

`FORMATTING.md:60` — "This preserves the original intent while making the
exception explicit and mechanically enforceable." This sentence is a chat
reply that was pasted along with the rule above it. It has no meaning in the
document.

### 2.5 `do` listed in the braces rule after do-while was banned

`FORMATTING.md:143` — "Always use braces for `if`, `else`, `for`, `while`,
`do`" while `FORMATTING.md:54` bans `do { ... } while`. Remove `do` from the
list.

### 2.6 Typos in author-owned text (report only)

`drafts/logs.md:8` "each each", `:58` "spawns several seconds" (spans),
`:59` "pring". These sit in the top half of a two-half document, which
`drafts/WRITING.md` reserves for the author. Not touched; listed for the
author.

## 3. Coverage and navigation

### 3.1 README index lists 9 of 17 drafts and none of the other directories

Not linked from `README.md`:

- `drafts/cli_main.md`, `drafts/endpoint_comment.md`, `drafts/var_names_error.md`,
  `drafts/formatting_blocks.md` (linked only from FORMATTING.md),
  `drafts/layout.md`, `drafts/logs.md`, `drafts/logs-cheatsheet.html`,
  `drafts/WRITING.md`, `drafts/interactions-should-return-only-boolean-flag.md`
- the whole `vue2/` directory (7 files)
- `packaging/packaging.md`
- `demos/`

A reader landing on GitHub cannot discover half the rulebook.

### 3.2 WRITING.md's own list of two-half documents is incomplete

`drafts/WRITING.md:44` names `logs.md` and `layout.md`. `drafts/refresh.md`
also carries the "AI-Generated Content Below" marker and follows the
convention.

### 3.3 The Naming Grammar block is duplicated verbatim

`README.md:130-201` ("Naming Grammar" through "Summary") is a copy of
`drafts/var_names.md` plus function rules. Two copies of the same table will
diverge. Keep one and link to it, or make README the canonical home and reduce
var_names.md to a pointer.

### 3.4 No enforcement despite claiming to be mechanically enforceable

`FORMATTING.md:60` calls the rules "mechanically enforceable", and most of
them are (brace placement by scope depth, 4-space indent, `else` on its own
line, sorted requires, `out` naming, `error` naming, no arrow blocks). There
is no ESLint config, no custom rule, no checker script in the repo. The demos
are the only executable content and nothing verifies they follow the rules
(see 1.2). A `bin/test` that runs the demos plus an ESLint config with the
expressible subset would turn the spec into a tool.

## 4. Repository hygiene

### 4.1 No `.gitignore`; `.idea/` is untracked but unprotected

`.idea/` shows as `??` in `git status`. `.idea/workspace.xml` contains a
local path (`/home/vb/w/rules`). One careless `git add .` publishes it.
A one-line `.gitignore` with `.idea/` fixes this. `drafts/layout.md` itself
lists `.gitignore` as a standard file.

### 4.2 Logo is stored twice in history, 2.6 MB of a 2.5 MB pack

`img/logo-by-chat-gpt.png` is 1.38 MB in the tree and a 1.26 MB earlier
version remains in history. Both copies are the bulk of the pack. Not worth a
history rewrite on a public repo, but the current file can be re-encoded
(a 400px-max logo does not need 1.4 MB) before the next README change.

### 4.3 Two committer identities

`git shortlog`: 56 commits as "Vladimir Barbaros", 15 as "Vladimir Barbarosh".
Add a `.mailmap` so blame and shortlog show one person.

### 4.4 Empty `repos/` directory

`repos/` exists locally, is empty, and git does not track empty directories.
Either it is scratch space (add to `.gitignore`) or it is a planned section
(add a README stub so it is tracked).

### 4.5 `packaging/packaging.md` is a template, not a rule

- Line 21 still carries the `__PROJECT_NAME__` placeholder.
- Line 60: `echo usage: ... 2>&1` sends usage to stdout; `>&2` was intended.
- Lines 31 and 66: `npm version $1 --git=/bin/true` is described as a hack;
  the supported flag is `npm version $1 --no-git-tag-version`.
- The script mixes backticks and `$(...)`, leaves `$1` unquoted, and lists
  pinned versions from 2020 (Vue 2.6.11, axios 0.19.1, Bootstrap 4.4.1).

The file is not linked from anywhere and reads as an imported note from
another project.

### 4.6 `vue2/vue-globals.md` relies on a private Vue internal

`vue2/vue-globals.md:23` builds ids from `this._uid`. That is an undocumented
Vue 2 internal, removed in Vue 3. Fine for a directory named `vue2`, but worth
a one-line warning since the mixin is presented as copy-paste ready.

## 5. What is good

- `FORMATTING.md` and `drafts/formatting_blocks.md` together give a complete,
  unambiguous layout spec. The two-tier brace rule is unusual and explained.
- `drafts/logs.md` bottom half is precise: value encoding, group semantics,
  producer-order definition of "after", limits. `logs-cheatsheet.html` matches
  it line for line.
- `drafts/naming_markers.md` resolves every naming question the README raises
  and records the rulings with reasons.
- Both HTML pages are self-contained: no scripts, no external CSS or fonts
  fetched, tags balanced. They render offline.
- No secrets anywhere, including history. The only "password" hits are the
  form-field examples.
- Every internal link resolves.

## 6. Recommended order of work

1. Resolve the four contradictions in section 1. Each is a one-file edit
   once the author decides which side wins.
2. Fix the typos in section 2 (2.1 and 2.4 first, they are in files a reader
   will copy from).
3. Add `.gitignore` (`.idea/`, `repos/` if scratch) and `.mailmap`.
4. Complete the README index (3.1) and collapse the duplicated grammar block (3.3).
5. Add a `bin/test` that at least runs `demos/*.js`, and an ESLint config for
   the enforceable subset (3.4).
6. Re-encode the logo (4.2), retire or finish `packaging.md` (4.5).
