# Project audit — 2026-09-20

Repository: `vbarbarosh/rules` (branch `main`, HEAD `cc91c84`, clean tree).
A coding-style rulebook which is also an ESLint plugin. 80 tracked files,
101 commits, first commit 2025-04-09, last 2026-09-20.

## Scope

The question of this audit is narrow: **which rules contradict other rules**.

Checks run:

- Every rule document was read in full: `README.md`, `FORMATTING.md`,
  `LINTING.md`, `docs/rules.md`, all of `drafts/*.md`, `vue2/*.md`,
  `glossaries/*.md`, `packaging/packaging.md`, plus `demos/*.js`,
  `src/config.js`, `bin/*`, `package.json`, and the previous audit note.
- Three documented examples were run through the linter
  (`eslint --config /app/eslint.projects.config.js`); the output is quoted in
  RULES-01, RULES-05 and RULES-18.
- Rule codes in `docs/rules.html` were counted and compared with
  `docs/rules.md` and `README.md`.
- Internal markdown links were resolved: 253 links, 0 broken.
- `npm run check`: lint clean, 179 tests in 33 suites pass.
- Every finding of `notes/audit-2026-09-02.md` was rechecked (section 9).

Not exercised:

- External links, secrets scan, git object sizes, HTML tag balance.
- The demo scripts were read, not executed.
- `formatting.html` and `drafts/logs-cheatsheet.html` were not compared with
  their specs; `docs/rules.html` was compared with `rules.md` by rule code
  only, not row by row.
- `src/rules/*.js` and `tests/*` were not reviewed. Only `src/config.js` and
  the gap/margin branch of `src/rules/vue_layout_classes.js:30-39` were read.

## Verdict

The main risk is unchanged since 2026-09-02: **documents which state the same
rule drift apart**. The rulebook has grown a linter and three new sources
(`LINTING.md`, `one_export_per_file.md`, `imports_sorted.md`), and each one
was written against the rule it needed, not against `FORMATTING.md`. Eight
rules are now directly contradicted by another document, and in three cases
the linter rejects an example the rulebook presents as canonical. Two of the
four contradictions of the previous audit are fixed; the classes one is
still open and has gained a third position.

## 1. Direct contradictions between rules

A reader following one document violates another.

### RULES-01 Classes: banned, catalogued, and allowed when extending (high)

Three positions:

- `FORMATTING.md:71` — "No classes, no prototypes, no mutation via shared
  state" (FLOW-09).
- `drafts/formatting_blocks.md:16-26` — `class Logger` with a constructor and
  a method, as a module-level catalog entry (FMT-05).
- `LINTING.md:107-108` and `src/config.js:25` — "no classes except one that
  extends another" (LINT-05).

`LINTING.md:5-6` says the plugin follows "the brace catalog in
`drafts/formatting_blocks.md`", yet the catalog's own `Logger` has no
superclass and the preset rejects it:

```
$ eslint --config /app/eslint.projects.config.js b.js     # class Logger { constructor(...) {...} }
  1:1  error  Use plain data structures and named functions; a class exists only to extend one  no-restricted-syntax
```

Related: `_to_` is reserved for "method position" (`tree.to_json()`, NAME-10,
`drafts/naming_markers.md:22`), which needs the objects with methods that
FLOW-09 bans.

Prior finding 2026-09-02 §1.1, still open, now with a third position.

### RULES-02 CommonJS-only against the ES-module rules (high)

- `FORMATTING.md:111-114` — "CommonJS modules only ... Do not use `import` or
  `export`" (FILE-17).
- `drafts/one_export_per_file.md:10-19` — "The rule is the same for both
  module systems", and every later example in the file is ESM (FILE-20,
  FILE-21, FILE-22).
- `drafts/imports_sorted.md:10` — "`require` and `import` alike" (FILE-08).
- `LINTING.md:72-73` — "JavaScript defaults to ES modules; `.cjs` uses
  CommonJS."

LINT-07 (`docs/rules.md:250`) reconciles them — "CommonJS-only is this
repository's own rule" — but `FORMATTING.md` never says that about itself,
and `rules.md:141` lists FILE-17 unconditionally next to FILE-20.

### RULES-03 The shared-state module against "no shared state" and "one function" (medium)

- `drafts/one_export_per_file.md:48-61` sanctions "a set of operations on
  shared state" as one object with `transport: null` and `run` (FILE-22).
- `FORMATTING.md:71` bans "mutation via shared state" (FLOW-09).
- `FORMATTING.md:32` — "Library modules export one function" (FILE-01,
  FN-16), not an object of many.

### RULES-04 The import block is one contiguous list, and two blocks (medium)

- `drafts/imports_sorted.md:40-41` — "No groups." "No blank lines and no
  comments inside the block" (FILE-11).
- `LINTING.md:94` — side-effect imports "form their own block at the top,
  kept in the order they run, and one blank line may separate it from the
  sorted named imports" (LINT-06).

The exception is reasoned, but the draft does not carry it.

### RULES-05 `gap*` position differs between the rule and the linter (medium)

- `drafts/css_classes.md:62-63` — a `gap*` "always comes directly after the
  layout class" (CSS-02).
- `LINTING.md:101` — "the flex/grid/split container, then its `flex-*`
  modifiers, then gap" (LINT-08); `src/rules/vue_layout_classes.js:30-31`.

`flex-row gap5 flex-wrap` satisfies CSS-02 and fails the linter:

```
$ eslint --config /app/eslint.projects.config.js a.vue
  4:20  error  Class "flex-wrap" is out of order: layout, spacing, sizing, ...  rules/vue-class-order
```

`flex-row flex-wrap gap5` passes.

### RULES-06 The `return out` headline is broken by its own carve-out (medium)

- `FORMATTING.md:118` — "If a variable is used in a `return` statement, it
  **MUST be named `out`**".
- `drafts/return_out.md:26-36` — `return lines.join('\n');` uses a variable
  in a return statement and is the right form; the draft saves itself with
  "`return out;`, exactly" on line 1. `FORMATTING.md` has no such carve-out.
- `LINTING.md:98` and `:180-182` narrow it again: only locally initialized
  arrays, objects and `new` results, and "passed-through parameters and
  outer-scope values are allowed".

### RULES-07 "Prepositions are neutral" against the marker table (medium)

- `drafts/naming_markers.md:4-5` — "Prepositions are neutral; the verb form
  decides the side."
- The table in the same file, `:21-23`, assigns `_from_`, `_to_` and `_of_`
  to the function side with no verb present.
- `README.md:130` — "A function name must contain a verb." `user_from_token`,
  `date_from_timestamp`, `descendants_of`, `json_from_tree` and
  `point_from_xy` contain none.

### RULES-08 `main` is not the single exception to domain-first naming (medium)

- `docs/rules.md:55` (NAME-18) — "`main` is the single exception to
  domain-first naming"; `FORMATTING.md:80` — "Functions and files follow
  `items_*`, `item_*`, or domain nouns".
- The rulebook itself sanctions verb-first families: `format_*`, `render_*`,
  `export_*`, `is_*`, `refresh_*`, `click_*`, `emit_*`.
- `drafts/refresh.md:26` uses `fetch_user()`; `drafts/var_names_error.md:6`
  uses `process_note()`, and `process` is on the generic-name list of
  `FORMATTING.md:81`.

`FORMATTING.md:36` says "the executable-entry exception"; "single" was added
by the index.

## 2. Weaker inconsistencies

### RULES-09 File order leaves no room for module-level statements (low)

`FORMATTING.md:132` — "No executable code other than `cli(main);` may appear
before the public entry function" (FILE-13). `drafts/formatting_blocks.md:28-41`
catalogs module-level `if`, `for` and `while` (FMT-06). Library order
(`FORMATTING.md:135`) has no slot for them, and the "global initialization"
of `FORMATTING.md:34` is itself executable code.

### RULES-10 `build/` is never committed, `dist/` is (low)

`drafts/layout.md:79-80` — `build/` is "Never committed, always reproducible"
(PROJ-04). `packaging/packaging.md:23-35` commits the build output as `dist/`
(REL-01, REL-02). Two directories and two policies for the same thing.

### RULES-11 The release script does not follow `bin/templ` (low)

`README.md:33` — "all scripts follow `bin/templ`, including strict mode,
temporary-directory cleanup, diagnostics, and colored exit messages"
(PROJ-15). The canonical `bin/release` in `packaging/packaging.md:44-73` has
strict mode only: no temporary directory, no `EXIT` trap, no exit message.
`bin/configure` is the same.

### RULES-12 Lookup is bracket access, yet `Map` is recommended (low)

`README.md:121-122` — "Lookup is bracket access, not a call" (NAME-03).
`FORMATTING.md:70` — "`Set`, `Map`, or plain `{}` for lookups". A `Map`
lookup is `user_by_id.get(id)`, a call.

### RULES-13 Modals return a boolean, `emit_end` returns a value (low)

`drafts/interactions-should-return-only-boolean-flag.md:8-12` — an
interaction returns a boolean commit flag (FN-14). `vue2/vue-globals.md:7` —
"`emit_end(retval)` for returning value from modal" (VUE-01).

### RULES-14 The theme is "not inherited", the first load reads the OS (low)

`drafts/theme_switch.md:14-16` — no follow-the-OS option "not even as the
default. The reader picks the theme on the page; he does not inherit it"
(UI-02). `:35-37` — with nothing stored, `prefers-color-scheme` is read
(UI-04). The mechanism is sound; the wording of UI-02 contradicts it.

### RULES-15 Transition placement: a rule in one file, a design call in another (low)

`drafts/css_classes.md:136-138` — the include "goes on the base rule, not on
the `:hover` / `.active` variant" (CSS-09). `LINTING.md:104` — "Whether a
transition belongs on the base rule or on a state is a design call".

### RULES-16 "Reset before setter" has an example doing the opposite (low)

`drafts/css_classes.md:101-107` — the heading says reset before setter; the
second example, `m5 xml`, puts the reset second. The text reconciles it
("the broad class leads ... whichever of the two is the reset"), so the real
rule is broad before narrow and the heading is wrong. The top half (`:11`)
says "usually come before setters", which is the author's text; report only.

### RULES-17 A route comment is neither intent nor policy (low)

`FORMATTING.md:84-87` — "Comments explain intent or policy only" (FMT-19).
The `METHOD /path (params)` comment of FMT-21 is neither, and
`drafts/endpoint_comment.md:8` itself tells it apart from "an intent
comment".

### RULES-23 A log line has "three fields", four are listed (low)

`drafts/logs.md:81` — "A line carries these three fields and nothing else."
The *Fields* section (`:96-141`) lists four: time, group_uid, sender,
details. LOG-02 speaks of "a fourth field" while `details` already is one.

## 3. Examples and indexes against a rule

### RULES-18 `vue-form.md` example breaks CSS-04 and its own prose (medium)

`vue2/vue-form.md:6` — `<app-form-div class="flex-row mi10">`. CSS-04
(`drafts/css_classes.md:93-94`): `mg*`/`mi*` are the block-container forms,
"the two do not mix". The example is the canonical form of VUE-09, and the
linter rejects it:

```
$ eslint --config /app/eslint.projects.config.js a.vue
  3:20  error  Use gap utilities to space flex/grid children; "mi10" belongs on block containers  rules/vue-layout-classes
```

Also `vue2/vue-form.md:3` says "Use `app-form-div` and `app-form-label`";
lines 7, 11 and 15 use `app-input-label`.

### RULES-19 `demos/items_by.js` returns a transformed `out` (low)

`demos/items_by.js:26-32` — `const out = {}; ... return Object.values(out);`.
VAR-13 (`drafts/return_out.md:26-27`): a value transformed on its way out is
not `out`.

### RULES-20 `demos/item_to.js` uses standalone `_to_` functions (low)

`demos/item_to.js:4-23` — `deg_to_rad`, `rad_to_deg`, `tuple_to_range`,
`range_to_tuple`, header "always a function". `drafts/naming_markers.md:39-41`
keeps `_to_` for method position. `LINTING.md:24-25` now admits the demos
"intentionally demonstrate invalid or superseded conventions", but the demo
itself does not say so. Prior finding 2026-09-02 §1.3.

### RULES-21 FN-13 attributes a sentence `refresh.md` does not contain (low)

`README.md:39` and `docs/rules.md:83` give `drafts/refresh.md` the rule
"derived state is never edited, only rederived".

```
$ grep -rn -i 'rederiv\|derived state' --include=*.md .
README.md:39: ...
docs/rules.md:83: ...
```

`refresh.md` speaks only of syncing a local copy of remote data.
`rules.md:3-4` says the cited document "stays the source of truth".

### RULES-22 README says 176 rules; there are 209 (low)

`README.md:31` — "all 176 of them". `docs/rules.md:6` — "209 rules", and
`docs/rules.html` carries 209 distinct codes, 33 of them UI/REL/DOC/LINT.
176 is the count up to the VUE group. `rules.md:8-9` ("a rule that page does
not carry is appended to the end of its group") is stale for the same reason.
